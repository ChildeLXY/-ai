# 全能高度开放 Agent 架构方案

> 基于现有大肥鱼AI 与 DeepBuddy 演进，不另起炉灶。
> 目标：一个本地优先、能力可热插拔、对外有标准协议、数据完全自主的通用 Agent。
> 日期：2026-11-18。

## 一、现状诊断（决定方案的起点）

| 组件 | 已具备 | 开放度短板 |
|---|---|---|
| 大肥鱼AI | 单文件插件热插拔、坏插件隔离、QQ/B站/桌宠/人格、云端代理 | 无依赖声明、无 schema 配置、插件跑在主进程、无标准对外协议 |
| DeepBuddy | 成熟 agent 循环、12 工具、安全门、三模式、19 专家、会话持久化 | 工具硬编码在 `TOOLS` 字典，扩展要改源码，不是插件系统 |

**结论**：DeepBuddy 强在"会干活"，大肥鱼强在"能扩展"。两者合并，缺的最后一块是**行业标准协议（MCP）**和**依赖注入内核**。

## 二、设计目标的精确定义

**"全能"** 覆盖七个面：模型、工具、agent 循环、记忆、多代理、多通道接入、桌面。

**"高度开放"** 满足五条硬标准：

1. 任何能力都是可热插拔插件，不重启主进程也能装/卸
2. 插件有依赖声明与配置 schema，不靠读源码
3. 支持行业标准 MCP（既能用外部工具，也能把自己暴露出去）
4. 提供本地 API/SDK，外部程序可直接调用
5. 数据本地、格式公开、可整体迁移，不被任何厂商锁定

## 三、总体架构（五层）

```
L4 前端层     桌面 UI（苹果简约风）/ Web / 桌宠 / 可观测面板
L3 接入层     QQ(OneBot) · B站 · 本地 HTTP API · MCP server · 插件市场
L2 协议层     MCP client · MCP server · JSON-RPC · 插件市场适配
L1 能力层     模型 provider · 工具 · 记忆 · 会话 · 子代理 · 安全沙箱（全是插件）
L0 内核层     服务注册表 + 依赖注入 · 生命周期 · 事件总线 · 配置 schema · 隔离
```

铁律：**L1 及以上的一切都是插件，内核本身不写业务。**

## 四、关键技术决策（明确选型，不骑墙）

### 1. 内核：Python 轻量依赖注入，不引入 Node

两个项目都是 Python、同 venv、同打包方式。自己写一个约 200 行的服务注册表即可，不需要 Cordis，也不背双运行时。

- 服务按名注册，插件用 `DEPENDS` 声明依赖
- 内核按拓扑序启动，缺依赖直接判定不加载（对应 DSH 的 inject 报错，但在安装阶段就拦下）
- 事件总线统一同步/异步两类

### 2. 插件契约升级（在现有大肥鱼契约上增量，向后兼容）

```python
PLUGIN_ID   = "xxx"                 # 沿用
PLUGIN_NAME = "中文名"              # 沿用
VERSION     = "1.0.0"
DEPENDS     = ["model", "storage"]  # 新增：依赖声明，决定加载顺序
CONFIG_SCHEMA = { ... }             # 新增：声明式配置，前端自动生成表单
ISOLATION   = "thread"              # 新增：safe / thread / process 三级
def setup(ctx): ...                 # 沿用
def apis(): ...                     # 沿用
def shutdown(): ...                 # 沿用
```

保留全部硬约束：单文件、不新增依赖、禁 C 盘/注册表/弹窗、网络 try/except、不 import 主程序。

### 3. 三级隔离

| 等级 | 场景 | 方式 |
|---|---|---|
| safe | 纯计算、只读 | 直接调用 |
| thread（默认） | 普通工具、网络 | 守护线程 + 超时 |
| process | 跑 Shell、不可信插件 | 独立子进程，崩溃不影响主程序 |

### 4. MCP 是开放度的核心，client 与 server 都做

- **MCP client**：任何外部 MCP 工具/资源自动变成可用工具，生态不靠自己造
- **MCP server**：大肥鱼的工具能被 Claude Desktop 等其他 agent 调用——这是"高度开放"的标志，也是和纯私有框架的本质区别
- 选型理由：MCP 是 2025 年后的行业标准，生命周期远长于任何私有插件协议

### 5. DeepBuddy 的 12 工具拆成内置插件

从硬编码 `TOOLS` 改为注册到内核的工具插件，可单独禁用/替换/升级，安全门与凭证保护作为独立策略插件保留。

### 6. 模型层统一为 provider 接口

本地 Ollama、云端 OpenAI 兼容（现有 cloud_proxy）、后续新厂商，都实现同一个 provider 接口，agent 不感知后端差异。重试、限流、token 计量作为独立插件。

### 7. 数据自主与可移植

全部本地存储，JSON/JSONL，文件带版本号（为迁移留口），可整体目录搬迁；不写注册表、不碰 C 盘。

## 五、分阶段路线（每阶段独立可验收）

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| P0 | 内核：DI 注册表 + 生命周期 + 事件总线 + schema | 服务可注册/解析；缺依赖明确报错；单测全过 |
| P1 | 插件契约升级 + 加载器（依赖序/隔离/热插拔） | 旧插件零改动可加载；坏插件隔离不拖垮主程序 |
| P2 | DeepBuddy 12 工具插件化 | 每个工具可单独开关；安全门仍生效 |
| P3 | 模型 provider 层（本地+云端） | 本地/云端各跑通一轮；后端可切换 |
| P4 | agent 循环 + 模式 + 专家 + 计划 | 多步任务自主执行；计划审批可拦截 |
| P5 | 记忆 + 会话持久化（版本化） | 重启后历史完整；旧数据可识别 |
| P6 | MCP client + server | 外部 MCP 工具可调；自身工具能被外部调用 |
| P7 | 子代理 / 多代理 | 子代理可派生回收；多代理任务可完成 |
| P8 | 开放 API + 插件市场对接 | 外部程序可经 API 调用；市场可安装 |
| P9 | 接入层（QQ/B站/桌宠）+ 前端 | 真实通道可用；UI 简约可观测 |
| P10 | 总体验收 + 打包 | 端到端用例全绿；安装包可在干净系统运行 |

## 六、与现有代码的复用映射（不浪费已有的东西）

| 现有产物 | 在新架构里的位置 |
|---|---|
| 大肥鱼插件体系（`plugins/__init__.py`） | 升级为 P1 加载器，契约向后兼容 |
| DeepBuddy 工具与 `run_task` | 拆成 P2 内置工具 + P4 默认 agent |
| cloud_proxy.py | P3 的一个云端 provider |
| DSH 市场桥接（dfy_market + host.mjs） | P8 插件市场来源之一 |
| QQ/B站/桌宠/人格记忆 | P9 接入层插件 |
| 安装前 probe 自测 | 保留为插件安装门，扩展到新契约 |

## 七、风险与应对

| 风险 | 应对 |
|---|---|
| 内核 DI 设计过度，拖慢交付 | 只做当前插件需要的能力，YAGNI，分小步提交 |
| 进程隔离增加复杂度 | 默认 thread，仅危险/不可信插件走 process |
| MCP 生态变化 | client/server 隔离实现，协议层可替换 |
| 升级期功能回归 | 每阶段验收门 + 旧契约兼容，任一时刻保留可用版本 |
| 体积膨胀 | 重型依赖按需安装，不进基础包 |

## 八、里程碑建议

- 第一里程碑（P0–P3）：内核 + 插件化 + 模型层，得到一个可扩展骨架
- 第二里程碑（P4–P6）：完整 agent + MCP，达到"全能且开放"
- 第三里程碑（P7–P10）：多代理 + 接入 + 前端 + 打包，成为可分发产品
